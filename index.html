HARNESS, NOT PROMPTS

别人改提示词，我们改 Harness

模型权重不动，被优化的对象是模型外面那套系统：系统提示、护栏、记忆、工具指引、技能、子代理、脚本、插件。 这八个组件才是大多数 agent 失败的真正原因——而我们把它当成可被反复改写的对象。

01

任务层 × 跨任务层：两层递归

每个任务先提案、再用真实执行对比、最后合成一份；被采纳的改法连同完整组件树写进同域经验库。 下一个任务先读经验，不必从零开始。

02

工作方式与行业口径，分开改

INV 只改“换个专业照样成立”的部分（流程、脚本、兜底），DOM 只改“这行人才知道”的口径与坑。 分开提案再合成——这是消融里贡献最大的一项。

03

没有标准答案，也能判断改对了

靠同一任务的多次执行对比：分叉（同一步做了不同选择）、重复失败（每次都在同一处错）、未发生的风险。 选择器挑交付物，评分结果永不回流给改进者。

04

沉淀的是完整组件树，不是总结

经验库存的是可执行的整棵树，配一份四字段说明：cue（什么时候翻这条）、lesson（该怎么做）、 evidence（哪次执行证明了它）、confidence（能不能推翻）。

05

把“静默失效”变成报错原文

技能没在常驻文本里被点名、脚本编译不过、常驻提示超预算——这三类错误在多数框架里不报错， 只是悄悄不生效。我们把它们拦在写入之前。

怎么验证我们没有吹

论文数字来自公开表格，我们只做算术复算；我们自己的效果以小规模 k=1 验证为准， 未验证的项不会写进对客材料。

看看我们怎么做的 ↗
−5.3去掉技能资产后的分数损失
−3.7去掉脚本资产后的分数损失
−1.5只把提示词写好，收益是最小的
+11.5同一方法在较弱执行器上的最大提升

数字出自 Google Research《Recursive Agent Harnessing for an Open World》(arXiv:2610.14224) 的公开表格（WorkBuddy 均分，k=5 组件消融与 k=1 主表），我们仅做算术复算。

快速开始

用 Docker 一键部署，或从源码运行：

# 方式一：Docker 一键部署（推荐，支持本地/国产模型）
docker compose -f deploy/docker-compose.yml up -d --build

# 方式二：从源码运行
git clone https://github.com/robin202208/JUDY-harness.git
cd JUDY-harness
pnpm install && pnpm run build && pnpm dsh web

# http://127.0.0.1:3080

Docker 方式需要 Docker；源码方式需要 Node.js ≥ 22.19 与 pnpm。运行后即可在界面中选择或创建你的专属 Agent 预设。
